# 의뢰서 입력 화면 배치

## Decisions

- 여러 개가 쌓이는 항목(해석 제품, 운전 조건, 선택 조건 패키지, Case)은 카드가 아니라 표 한 줄로 보여 주고, 행을 추가해 늘린다. 한 행에 다 담기지 않는 세부(팬별 설정 등)는 그 행 바로 아래에 펼친다.
- 한 번만 입력하는 항목은 짧은 칸을 2열로 묶는다. 사용자 정보처럼 이미 아는 값은 한 줄 요약으로 접고 "수정"을 눌러야 펼친다. 필수가 아닌 항목은 "선택 항목"으로 접는다.
- 사용 여부를 골라야 하는 선택 조건은 별도 요약 카드 없이 각 조건의 제목 줄에 "있음·없음"을 둔다. "없음"이면 제목 한 줄만 남고, "있음"이면 그 자리에서 입력 표가 펼쳐진다. 아직 고르지 않은 상태는 두 버튼 모두 눌리지 않은 채 "선택 필요"로 표시한다.
- 단계 버튼에 완료, 남은 항목 수, 확인 필요를 늘 표시하고, 이전·다음(마지막 단계에서는 제출)은 화면 하단에 고정한다.
- 긴 안내 문구는 제목 옆 도움말 아이콘 뒤에 둔다. 화면에는 한 줄 이내의 안내만 남긴다.

## Boundaries

- 의뢰자가 작성하는 의뢰서 화면에 적용한다. 목록, 상세 조회, 관리자 검토 화면에는 강제하지 않는다.
- 새 해석유형을 추가할 때도 같은 규칙을 쓴다. 조건 그룹이 늘어도 반복 항목은 표, 사용 여부는 제목 줄이다.
- 좁은 화면에서 표가 가로로 스크롤되는 것은 허용한다. 휴대폰 전용 카드 배치를 따로 만드는 결정이 아니다.
- 일반 UI 구성 요소와 토큰은 `ui-composition.md`를 따른다.

## Why

첫 구현은 단계로 나눴는데도 모든 입력 칸을 라벨과 안내와 함께 세로로 쌓아서, 의뢰 내용·해석 제품·해석조건 모두 스크롤이 길고 복잡해 보였다. 같은 데이터로 비교했을 때 표 방식은 해석조건 화면 길이를 약 2,600px에서 930px로 줄였고, 운전 대안끼리 값을 나란히 비교할 수 있었다. 의뢰자는 주로 PC에서 작성하는 기구설계 엔지니어라 좁은 화면의 불편은 작다고 판단했다.

## Reconsider when

- 의뢰서를 휴대폰이나 태블릿에서 작성하는 비율이 높아질 때.
- 도움말 뒤로 옮긴 안내 때문에 조건 불명확·조건 오류 보완 요청이 눈에 띄게 늘 때.
- 한 의뢰의 운전 대안이나 조건 패키지가 거의 항상 하나뿐이어서 표로 비교할 일이 없을 때.

## Still-rejected alternatives

- 항목마다 카드로 세로로 쌓는 방식(첫 구현) — 입력 칸이 많아질수록 스크롤이 길어지고 대안끼리 비교가 어렵다; 휴대폰 작성이 주가 되면 다시 본다.
- 한 줄 요약 목록과 편집 패널 — 평소 화면은 가장 단순하지만 값을 바꿀 때마다 한 번 더 눌러야 하고 대안을 나란히 고치기 어렵다; 패키지 수가 아주 많아지면 다시 본다.
- 질문을 하나씩 보여 주는 질문형 — 처음 쓰는 사람에게 쉽지만 클릭이 가장 많고 전체를 한눈에 보기 어렵다; 목적부터 묻는 시작 화면을 정할 때 함께 본다.
- 선택 조건 사용 여부를 화면 위 요약 카드에 모으는 방식 — 공간을 많이 차지하고 아래 섹션과 같은 내용이 두 번 나온다.
- 사용 여부를 체크박스 한 줄로 받는 방식 — "체크 안 함"이 "없음"인지 "아직 안 정함"인지 구분되지 않아 명시적으로 없음을 고르게 한 규칙과 충돌한다.
