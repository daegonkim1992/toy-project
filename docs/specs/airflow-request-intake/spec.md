# 풍량 해석 의뢰 접수

## 목적

기구설계 엔지니어(의뢰자)가 풍량 해석 의뢰서를 작성해 제출하고, 해석관리자가 이를 검토해 접수하거나 보완을 요청하는 것까지를 플랫폼에서 끝낸다. 해석팀이 메일·전화로 목적과 조건을 되묻는 일을 의뢰서의 필수 항목과 제출 조건, 보완 요청과 재제출로 대신하고, 의뢰와 그 이력이 한 곳에 쌓이게 한다.

대표 상황: 에어컨 실외기의 팬이 바뀌었을 때 풍량이 얼마나 달라지는지 확인하려는 의뢰자가 기존 팬 형상(Base)과 변경 팬 형상(비교 제품)을 놓고 풍량 해석을 의뢰한다.

## 적용되는 제품 제약

- 서비스는 의뢰 접수를 해석팀 대신 맡는다. 해석 수행과 보고서 작성은 이 서비스의 범위가 아니다.
- 조건, 변경 이력, 결과를 나중에 쓸 수 있는 구조로 빠짐없이 쌓는다. 이 작업에서는 의뢰서 내용, revision, 상태 변화 이력이 해당된다.
- 해석에 익숙한 의뢰자도, 상황이 애매한 의뢰자도 같은 경로로 의뢰한다. 이 작업은 풍량 해석 하나만 다루므로 해석유형 선택과 목적 기반 안내는 보류다(보류 항목 참고).

## 사용자에게 보이는 결과

1. 의뢰자는 단계별 화면을 따라 풍량 해석 의뢰서를 작성하고, 저장해 두었다가 이어 쓰고, 빠진 곳을 확인한 뒤 제출한다.
2. 해석관리자는 제출된 의뢰를 검토해 사유와 함께 보완을 요청하거나, 해석담당자를 지정해 접수한다.
3. 의뢰자는 보완 요청을 받으면 해당 사유를 보고 수정해 다시 제출한다.
4. 각 역할은 자기가 처리할 의뢰를 할 일 목록에서 보고, 의뢰별 진행 이력을 확인한다.
5. 접수된 의뢰는 "해석 진행 중" 상태가 되고, 배정된 담당자가 의뢰서를 조회할 수 있다.

| 목록과 이력 | 역할별 할 일 목록, 상태별 건수, 상태 변화 이력, revision |
| 기준 데이터 | 임시 샘플 데이터(제품 분류, 열교환기 Catalog, PMS 프로젝트) |

### 범위 밖 (이유와 함께)

- **설치 조건**: 업무정의서에서 세부 항목이 [추후 정의](3D 기능 완성 후)다.
- **반려, 해석 중 보완 요청, 보류, 재개, 재배정, 진행 중 변경, 취소 요청**: 해석이 시작된 뒤의 흐름이며, 이 작업은 접수까지만 다룬다.
- **결과 등록, 결과 확인, 결과 재작업 요청**: 결과 회신은 후속 작업이다.
- **앱 내 알림**: 할 일 목록으로 처리할 일을 확인할 수 있어 후속으로 둔다.
- **다른 10종 해석유형**: 조건 구성이 달라 후속 작업에서 하나씩 붙인다.
- **실제 로그인과 사용자 관리**: 업무정의서가 사용자, 역할, 소속 부서를 개발자가 관리한다고 전제한다.
- **성과 지표 화면**: 성공 지표가 정해지지 않았다.

## 확정한 제약과 근거

- **사용자 전환**: 실제 로그인을 만들지 않고 샘플 사용자를 화면에서 전환한다. 의뢰자는 소속 부서가 같은 2명 이상과 다른 부서 1명 이상, 해석관리자 1명 이상, 해석담당자 1명 이상을 둔다. 근거: 로그인은 이 업무의 핵심이 아니고, 같은 부서 조회 규칙을 확인하려면 의뢰자가 여럿 있어야 한다.
- **단계별 작성**: 의뢰 대상, 의뢰 내용, 해석 제품, 해석조건, Case, 최종 검토 순으로 단계를 나눈다. 근거: 앞 단계가 뒤 단계를 정하는 의존 관계(업무정의서 4.6)가 있고, 앞 단계가 바뀌었을 때 다시 볼 곳을 알려 주기 쉽다.
- **선택 조건 포함**: 공간 압력, 열교환기, 필터를 이번 단위에 포함한다. 사용자의 결정이다.
- **임시 샘플 기준 데이터**: 제품 분류, 열교환기 Catalog, PMS 프로젝트 목록은 실제 파일이 없어 임시 샘플로 채운다(아래 위험 참고). 사용자의 결정이다.
- **풍량 해석 조건 구성**: 운전(필수), 공간 압력·열교환기·필터(선택)로 한다. 설치는 위 범위 밖 이유로 표시하지 않는다. 업무정의서 매핑표에서 풍량 해석에 설치가 선택(○)이지만 이번에는 제외한다.
- **화면 구성**: 일반 UI는 `docs/decisions/ui-composition.md`를 따른다.
- **의뢰서 화면 배치**: 승인된 시안(`prototype.html`)과 `docs/decisions/request-form-layout.md`를 따른다. 근거: 첫 구현은 단계로 나눴어도 입력 칸이 세로로 길게 쌓여 복잡해 보였다. 해석조건 단계에서 현재 화면(A), 표로 압축한 안(B), 요약 목록과 편집 패널(C), 질문형(D)을 비교해 B를 골랐고, 선택 조건의 사용 여부는 별도 요약 카드 대신 각 조건의 제목 줄에 두기로 했다. 같은 규칙을 6단계 전체에 적용한 시안을 사용자가 승인했다.
- **단계 진행 상태**: 각 단계 버튼에 완료(✓), 남은 항목 수, Case 확인 필요를 표시한다. 최종 검토는 단계별 요약 카드에 그 단계의 빠진 항목과 해당 단계로 이동하는 수정 링크를 함께 보여 준다. 근거: 빠진 항목을 최종 검토에 가서야 알 수 있었다.
- **Case 선택 방식**: 운전 조건 외의 활성 열이 모두 선택지 하나뿐이면 형상 × 운전 조건 체크 격자로 고르고, 하나뿐인 선택지는 모든 Case에 자동으로 들어간다. 선택지가 둘 이상인 열이 있으면 행 단위 표로 고른다. 두 방식 모두 "전부 선택(전부 조합)" 버튼을 둔다. 모든 조건을 자동으로 곱해 기본값으로 만들지는 않는다(업무정의서 6장).

## 인수 기준

### 의뢰자

- 작성 중인 의뢰는 저장되고, 브라우저를 닫았다가 다시 열어도 같은 의뢰자가 이어 쓸 수 있다.
- 의뢰 대상 확정 시 의뢰번호가 `CFD-YYYYMMDD-NNN` 형식으로 발급된다(NNN은 날짜별 일련번호). 같은 날 두 번째 의뢰는 다른 번호를 받는다.
- 제품 분류는 등록된 조합에서만 고를 수 있고, 등록되지 않은 조합을 만들 수 없다.
- 의뢰 유형이 개발 프로젝트이면 제품 사업부에 해당하는 PMS 프로젝트를 골라야 하고, 고르면 개발 등급과 NPI 단계가 필수가 된다. 다른 유형에서는 요구하지 않는다.
- 희망 완료일이 의뢰 요청일보다 앞서면 제출할 수 없다.
- Base 제품은 정확히 1개다. 모든 제품에 도면번호(영문·숫자·하이픈)가 있어야 하고 제품끼리 중복될 수 없다. 비교 제품마다 Base 대비 차이 설명이 있어야 한다.
- 운전 조건: 팬 개수는 1~10이다. 회전수 설정이 "팬별 설정"이면 팬마다 회전수와 팬 위치를 받는다. 풍량을 입력하면 풍량 활용 목적(해석에 반영 요청 / 참고 정보로 제공)이 필수가 된다. 회전수가 없고 풍량이 있으면서 활용 목적이 "참고 정보"인 조합은 제출할 수 없다. 회전수도 풍량도 없는 운전 조건은 제출할 수 없다.
- 여러 운전 대안은 운전 조건 패키지를 여러 개로 만들고, 한 패키지 안의 여러 팬은 동시 구성으로 입력한다.
- 열교환기 사양(유형, 관 직경 또는 채널 폭, Fin type, 열 수, FPI)은 샘플 Catalog에 있는 조합이어야 제출할 수 있다. "열교환기 없음"을 고르면 사양을 요구하지 않는다.
- 필터를 쓰기로 하면(제품에 필터가 있음 체크) 필터 패키지, 물리적 필터, 측정점(유속·압력손실, 1개 이상)을 입력해야 한다. 체크하지 않으면 요구하지 않고 Case에는 "없음"으로 보인다.
- 공간 압력은 값 또는 "없음"을 선택해야 하고, 선택하지 않은 빈 상태로는 제출할 수 없다. 공간 온도 등 매핑에 없는 항목은 화면에 나타나지 않는다.
- "없음"을 선택하거나 사용 체크를 해제해도 이미 입력한 값은 지워지지 않고, 다시 켜면 복원된다. Case와 최종 검토에는 "없음"으로 보인다.
- 모든 자유 입력은 200자를 넘을 수 없다.
- Case: 형상마다 기본 1행이 생기고, 활성 열(형상과 운전, 공간 압력, 열교환기, 필터)을 모두 선택해야 한다. 형상과 활성 조건이 모두 같은 Case는 만들 수 없다. 입력한 형상과 조건 패키지는 최소 한 Case에서 쓰여야 한다.
- 제품이나 조건을 바꾸면 사라진 선택은 비워지고, Case 구성을 다시 확인받아야 제출할 수 있다.
- 제출 조건을 충족하지 못하면 제출이 막히고, 최종 검토 단계에서 미충족 항목의 위치가 보인다.
- 제출하면 상태가 "검토 중"이 되고 revision 1이 남는다. 검토 중에는 의뢰서 내용을 수정할 수 없다.
- 보완 필요 상태에서만 의뢰서를 수정해 재제출할 수 있고, 재제출하면 "검토 중"이 되며 revision이 하나 늘어난다.
- 의뢰자는 작성 중, 검토 중, 보완 필요 상태에서 의뢰를 취소할 수 있다. 취소된 의뢰는 조회만 가능하며, 취소된 번호는 다시 쓰이지 않는다.
- 의뢰자는 자기 의뢰와, 로그인한 사용자와 소속 부서가 같은 사용자가 만든 의뢰를 볼 수 있다. 같은 부서 의뢰는 조회만 가능하고 수정·제출·취소 메뉴가 보이지 않는다. 다른 사용자의 작성 중 의뢰는 보이지 않는다.

### 해석관리자

- 검토 중인 의뢰를 모두 볼 수 있고, 할 일 목록에는 검토 중인 의뢰가 들어 있다.
- 보완 요청에는 사유 코드(7개 중 하나)와 설명이 필수이며, 제출하면 상태가 "보완 필요"가 된다.
- 접수하려면 해석담당자를 지정해야 하고, 접수하면 상태가 "해석 진행 중"이 된다.
- 재제출된 의뢰에서 이전 revision과 달라진 항목을 볼 수 있다.

### 해석담당자

- 자기에게 배정된 의뢰만 볼 수 있고, 의뢰서 내용을 조회할 수 있다. 의뢰서를 수정할 수는 없다.

### 공통

- 모든 기능은 정해진 상태에서만 메뉴로 보인다. 예: 취소는 접수 이후에는 보이지 않고, 재제출은 보완 필요 상태에서만 보인다.
- 각 상태 변화는 수행자, 이전·이후 상태, 사유, 시각이 이력에 남고 의뢰별로 볼 수 있다.
- 각 역할의 할 일 목록은 해당하는 의뢰를 상태별 건수와 함께 보여 준다. 의뢰자: 작성 중, 보완 필요. 해석관리자: 검토 중. 해석담당자: 본인에게 배정된 해석 진행 중.
- 접수된 이후(해석 진행 중, 취소) 의뢰는 이 작업의 기능으로는 더 이상 변경되지 않는다.
- 샘플 기준 데이터에는 제품 분류 조합 여러 개(해석 범위와 운전 구분 같은 조건부 항목이 나타나는 조합을 포함), PMS 프로젝트 여러 개, 열교환기 Catalog 조합 여러 개가 있어, 위 조건들이 실제로 동작하는지 확인할 수 있다.

## 가정 (이의가 있으면 바꿀 수 있는 선택)

- 의뢰번호 형식은 `CFD-YYYYMMDD-NNN`이다. 업무정의서에서 [검토 필요]인 초안 규칙을 채택한다.
- 희망 완료일은 의뢰 요청일보다 앞설 수 없다. 같은 이유로 채택한다.
- 보완 요청 사유 코드 7개(정보 누락, 조건 불명확, 조건 오류, 형상 미비, 목적 불명확, 해석유형 부적합, 기타)는 업무정의서 3.7의 초안을 채택한다.
- 제품 풍량 입력은 단위 하나를 고정해 라벨에 표시한다(예: m³/min). 업무정의서에서 지원 단위가 [추후 정의]라서 임시로 정한 값이다. 바뀔 결정: 풍량 지원 단위 정의.
- 사용자와 부서는 샘플 사용자에 미리 정해 둔다. 의뢰서의 "부서" 칸은 직접 입력하는 값이라 조회 범위 기준으로 쓰지 않는다.
- 취소만 지원하고 반려는 뺀다. 취소는 의뢰자가 접수 전에 직접 종료하는 기능이다.
- 해석 제품 표에서 긴 Base 대비 차이는 한 줄로 잘리고, 마우스를 올리면 전체가 보인다.
- 좁은 화면(휴대폰 폭)에서는 해석 제품과 해석조건의 표가 표 안에서 가로로 스크롤된다. 표 대신 카드로 바꾸는 처리는 하지 않는다.
- 의뢰자 정보는 사용자 정보로 미리 채운 한 줄 요약으로 보이고, "수정"을 누를 때만 입력 칸이 펼쳐진다. 결과 활용 목적은 "선택 항목"으로 접어 둔다.

## 보류한 항목

| 항목 | 이번 작업에서의 임시 처리 | 대체할 결정 |
|---|---|---|
| 해석유형 선택과 목적 기반 안내 (PRODUCT.md의 경험 원칙) | 풍량으로 고정. 해석유형 선택 화면 없음 | 해석유형 선택과 안내 작업 |
| 설치 조건 | 표시하지 않음 | 설치 조건 세부 정의 (3D 기능 완성 후) |
| 풍량 지원 단위 | 단위 하나를 고정 | 업무정의서의 풍량 단위 정의 |
| 측정·판정 기준 표준값 | 풍량 해석에는 해당 항목이 없어 이번 작업과 무관 | 후속 해석유형 작업 |
| 기준 데이터 원본 | 임시 샘플 사용 | 실제 파일로 교체 |
| 실제 로그인과 사용자 관리 | 샘플 사용자 전환 | 인증 도입 작업 |
| 반려, 해석 중 흐름, 결과 회신, 알림 | 없음 | 후속 작업 단위 |

## 남은 위험

- **샘플 기준 데이터와 실제 데이터의 차이**: 열교환기 Catalog 조합과 제품 분류가 실제와 달라서, 샘플에서는 제출되는 의뢰가 실제 데이터에서는 막히거나 반대가 될 수 있다. 실제 파일로 교체한 뒤 제출 조건을 다시 확인해야 한다.
- **풍량 단위**: 임시 단위가 실제 사용 단위와 다르면 의뢰자가 값을 잘못 입력할 수 있다.
- **업무정의서의 초안 규칙**: 사유 코드, 의뢰번호, 알림 대상 등 [검토 필요] 항목이 바뀌면 이 명세의 해당 부분도 바뀐다.
- **해석팀 합의 부족**: 업무정의서의 역할과 흐름이 해석팀의 실제 업무와 맞는지는 검증되지 않았다. 접수 단계에서 해석관리자가 쓰는 판단 정보가 충분한지 사용해 보면서 확인해야 한다.
- **안내 문구 접기**: 긴 안내를 도움말 아이콘 뒤로 옮겼으므로, 해석을 잘 모르는 의뢰자가 운전 대안과 동시 팬, 풍량 활용 목적을 혼동할 수 있다. 보완 요청 사유(조건 불명확·조건 오류)가 늘어나는지 지켜봐야 한다.
- **휴대폰 사용**: 의뢰서를 휴대폰에서 자주 쓴다면 표의 가로 스크롤이 불편하다.
- **범위의 크기**: 선택 조건 3종과 Case 규칙까지 포함해 첫 단위치고 크다. 구현 중 분리가 필요하면 `split-into-tasks`로 나눈다.
