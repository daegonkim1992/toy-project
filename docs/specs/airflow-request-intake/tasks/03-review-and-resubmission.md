# 03 — 검토·접수·보완 요청·재제출·취소

## Outcome

해석관리자가 제출된 의뢰를 검토해 해석담당자를 지정해 접수하거나, 사유 코드와 설명으로 보완을 요청한다. 보완을 요청받은 의뢰자는 의뢰서를 수정해 재제출하고, 관리자는 이전 revision과 달라진 항목을 본다. 의뢰자는 접수 전에 의뢰를 취소할 수 있다. 해석담당자는 배정된 의뢰를 조회한다. 각 역할은 자기가 처리할 의뢰를 상태별 건수와 함께 할 일 목록에서 보고, 의뢰별 상태 변화 이력을 확인한다.

## Blockers

01. 검토할 제출된 의뢰와 revision, 이력 구조가 01에서 만들어진다. 02와는 독립이라 02 없이 진행해도 된다.

## Acceptance criteria

- [ ] 해석관리자는 검토 중인 의뢰를 모두 볼 수 있고, 할 일 목록에 검토 중 의뢰가 들어 있다.
- [ ] 보완 요청은 사유 코드 7개 중 하나와 설명 없이는 제출할 수 없고, 제출하면 상태가 "보완 필요"가 된다.
- [ ] 접수는 해석담당자를 지정해야 하고, 접수하면 상태가 "해석 진행 중"이 된다.
- [ ] 의뢰자는 보완 필요 상태에서만 의뢰서를 수정해 재제출할 수 있고, 재제출하면 "검토 중"이 되며 revision이 하나 늘어난다. 보완 필요 외 상태에서는 수정과 재제출 메뉴가 보이지 않는다.
- [ ] 관리자는 재제출된 의뢰에서 이전 revision 대비 달라진 항목을 볼 수 있다.
- [ ] 의뢰자는 작성 중, 검토 중, 보완 필요 상태에서 의뢰를 취소할 수 있다. 접수 이후에는 취소 메뉴가 보이지 않는다. 취소된 의뢰는 조회만 가능하고, 취소된 번호는 다시 쓰이지 않는다.
- [ ] 해석담당자는 자기에게 배정된 의뢰만 볼 수 있고, 의뢰서 내용을 조회할 수 있으며 수정할 수는 없다.
- [ ] 역할별 할 일 목록이 상태별 건수와 함께 보인다. 의뢰자: 작성 중, 보완 필요. 해석관리자: 검토 중. 해석담당자: 본인에게 배정된 해석 진행 중.
- [ ] 모든 상태 변화(제출, 보완 요청, 재제출, 접수·배정, 취소)가 수행자, 이전·이후 상태, 사유, 시각과 함께 이력에 남고 의뢰별로 볼 수 있다.
- [ ] 접수("해석 진행 중")와 취소 이후의 의뢰는 이 작업의 기능으로 더 이상 바뀌지 않는다.

## Constraints

- 기능은 정해진 상태에서만 메뉴로 보인다.
- 반려, 해석 중 보완 요청, 보류, 재배정, 진행 중 변경, 취소 요청, 결과 등록, 앱 내 알림은 만들지 않는다(명세의 범위 밖).
- 사유 코드 7개는 업무정의서 3.7의 초안을 채택한 가정이다(명세의 가정).
- 상태와 기능의 세부, 보이는 상태는 [해석의뢰 업무정의서](../../../../해석의뢰%20업무정의서.md)의 2장, 3.1~3.5, 3.7을 따른다. 이 작업에 해당하는 부분만 적용한다.
- 화면 구성은 [docs/decisions/ui-composition.md](../../../decisions/ui-composition.md)를 따른다.

## Verification

- 단위 테스트: 상태 전이와 각 상태에서 허용되는 기능, 필수 입력(사유 코드·설명, 담당자), 역할별 조회 범위와 할 일 목록 구성, 재제출 시 revision 증가와 달라진 항목 계산이 기대한 결과를 낸다.
- E2E: 제출 → 보완 요청 → 재제출 → 접수 흐름이 끝까지 이어지고 이력에 각 단계가 남으며, 접수된 의뢰는 담당자가 조회하고 의뢰자는 취소 메뉴를 볼 수 없다. 접수 전 취소는 의뢰를 취소 상태로 만든다.
